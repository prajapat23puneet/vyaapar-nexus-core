Project name: VyaaparNexus

One-line definition:
A live distributed e-commerce order orchestrator where a user can place a demo order, watch a real multi-step saga complete in real time, and trigger controlled failure paths to observe compensating transactions, backpressure, and resilience behavior.

Primary demo outcomes:
1. User visits live dashboard.
2. User clicks "Place Demo Order".
3. Backend creates a real order, persists saga state, writes outbox messages, publishes events via RabbitMQ.
4. Frontend receives real SSE updates and shows:
   - active saga count
   - current service step
   - orders/min
   - p95 latency
   - outbox pending
   - dead letters
   - circuit state
5. User can trigger:
   - payment failure
   - inventory failure
6. System shows correct compensation path, updates DB, restores stock where required, marks terminal status.

Non-goals:
- No user login/auth system
- No payment gateway integration
- No real shipping provider integration
- No email sending
- No admin CMS
- No multi-tenant support
- No Kubernetes
- No paid services
- No E2E browser automation tests

Logical domain flow:
- Order submission starts in API
- API persists order + items + saga state + outbox in one transaction
- Background outbox publisher publishes integration event to RabbitMQ
- Worker consumers process saga stages
- Each stage updates business state and saga state
- Metrics snapshot service aggregates system metrics
- SSE endpoint streams current metrics and active saga state to frontend

Canonical service sequence:
Order → Inventory → Payment → Shipping → Notification → Completed

Failure branches:
- Inventory failure before reservation finalization
- Payment failure after inventory reservation, requiring compensation

Purpose:
Transactional Outbox for guaranteed message publication.

Columns:
- id UUID PK
- correlation_id UUID NOT NULL
- message_type VARCHAR(200) NOT NULL
- payload JSONB NOT NULL
- exchange VARCHAR(200) NOT NULL
- routing_key VARCHAR(200) NOT NULL
- created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
- published_at TIMESTAMPTZ NULL
- retry_count INT NOT NULL DEFAULT 0
- last_error TEXT NULL

Indexes:
- idx_outbox_unpublished(created_at) where published_at is null
- idx_outbox_correlation(correlation_id)

Behavior:
- API and consumers write outbox messages in same transaction as domain state changes
- background publisher drains pending rows in batches
- rows remain for audit even after publish

Purpose:
Idempotency guard for consumers.

Columns:
- id UUID PK
- message_id VARCHAR(200) NOT NULL UNIQUE
- consumer_name VARCHAR(200) NOT NULL
- correlation_id UUID NULL
- processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()

Indexes:
- unique(message_id)
- idx_inbox_consumer(consumer_name, processed_at desc)

Behavior:
- Before consuming a message, consumer checks if message_id already processed
- If yes, short-circuit and ack
- If no, process and insert row in same transaction if feasible

Idempotency key:
- Prefer broker message ID if available
- else deterministic contract field + correlation id + consumer name hash

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Header:
X-Api-Key: <plaintext key>

Rules:
- Required on every /api/* endpoint except health and metrics if desired
- Required on SSE endpoint too
- Frontend sends key on axios and fetch-event-source
- Missing key => 401
- Invalid key => 401
- Inactive key => 401

Hashing flow:
1. Read header
2. SHA-256 hash plaintext
3. Compare against api_keys.key_hash
4. On success update last_used

Do not:
- hardcode accepted plaintext key in middleware
- bypass auth for demo order endpoint
- expose hash in any API response

Canonical error:
{
  "error": "Invalid API key"
}

- X-Force-Failure optional: payment | inventory

Request body:
{
  "customerId": "uuid",
  "paymentMethod": "UPI",
  "shippingAddress": {

      "quantity": 2
    }
  ]

Validation:
- customerId required and must exist
- paymentMethod required and valid enum
- shippingAddress required
- items required, min 1
- each item.productId required and must exist
- each quantity >= 1
- product must be active
- no duplicate productId entries in single request; merge or reject consistently
- totals must be computed on server, not trusted from client

{

  "correlationId": "uuid",

  "sagaUrl": "/api/orders/{id}/saga"
}

Failure responses:
- 400 invalid payload
- 404 customer or product missing
- 409 invalid product state if inactive
- 401 invalid key
- 500 unexpected

Error shape:
{
  "error": "Validation failed",
  "details": {
    "items[0].quantity": ["Quantity must be greater than 0"]
  }
}

  "outboxPending": 1,
  "ordersPerMinute": 2.4,

      "correlationId": "uuid"
    }

Source of each field:
- activeSagas => saga_states count non-terminal
- deadLetterCount => RabbitMQ management API or tracked dead-letter queue count
- outboxPending => outbox_messages where published_at is null
- ordersPerMinute => count orders created within trailing 60s
- sagaSuccessRate => completed / (completed + cancelled) over trailing window or all-time; choose and document consistently, recommend trailing 24h
- p95LatencyMs => percentile derived from completed saga durations
- cpuPercent => process-level/system metric
- memoryPercent => process-level/system metric
- circuitStates => CircuitBreakerStateMonitor
- activeOrder => latest non-terminal order
- recentLogs => in-memory rolling buffer or stream snapshot from Serilog sink adapter

No fake values.
No front-end interpolation.
No simulated logs.

15. SAGA FLOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Final state machine behavior:

Happy path:
1. POST /api/orders
2. Create order + items + saga_state + event_log + outbox row in one transaction
3. Outbox publishes OrderCreated
4. Worker consumes OrderCreated
5. Inventory step checks stock and reserves inventory
6. Inventory success writes saga_state update + event_log + outbox PaymentProcessRequested
7. Payment step succeeds
8. Payment success writes state + event_log + outbox ShippingDispatchRequested
9. Shipping step succeeds
10. Shipping success writes state + event_log + outbox NotificationSendRequested
11. Notification succeeds
12. Final state marked OrderCompleted
13. duration_ms computed from started_at to completed_at

Inventory failure path:
1. OrderCreated consumed with forceFailure=inventory or insufficient stock
2. Inventory reservation fails
3. saga_state current_state = InventoryFailed then OrderCancelled or directly OrderCancelled, choose explicit two-step preferred for trace clarity
4. orders.status = OrderCancelled
5. failure_reason = inventory reason
6. no stock restoration needed if reservation never succeeded
7. append event log entries for failure and terminal cancellation

Payment failure path:
1. Inventory reservation succeeds
2. Payment step fails due to forceFailure=payment or simulated rejection
3. saga_state current_state = PaymentFailed
4. compensation step restores stock
5. orders.status = OrderCancelled
6. failure_reason = payment reason
7. append event logs for PaymentFailed, InventoryReleased, OrderCancelled

Strong recommendation:
- Maintain explicit event log entries even when some states are not persisted in orders table
- Keep order.status aligned with externally visible major state
- Keep saga_state richer than order.status

16. INVENTORY CONSISTENCY RULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Inventory handling requirements:
- Reservation must be atomic enough to prevent double decrement
- Use distributed lock per product or per order depending implementation
- Preferred lock key:
  inventory:product:{productId}
- For multi-item order:
  - acquire locks in deterministic sorted productId order
  - fail fast if unable to acquire any lock
  - release all locks in finally block
- Within DB transaction:
  - verify stock_quantity >= requested
  - decrement stock_quantity
- On payment failure compensation:
  - increment stock_quantity by reserved amount

Do not:
- reserve stock in memory only
- assume single worker instance
- decrement stock without lock + transaction

17. CIRCUIT BREAKER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Apply circuit breaker to simulated external call layer:
- PaymentService
- optionally ShippingService/NotificationService, but Payment is mandatory

Config:
- break after 3 consecutive failures
- duration 30 seconds
- half-open allow 1 probe or small probe count
- state transitions captured in CircuitBreakerStateMonitor

Monitor responsibilities:
- maintain current state per service
- expose current states to SSE snapshot layer
- update on onBreak, onReset, onHalfOpen callbacks

UI must reflect:
- Closed => normal
- Open => red + OPEN badge + bolt icon
- HalfOpen => amber + HALF-OPEN badge

If payment circuit is open:
- treat payment attempt as failed immediately
- proceed to compensation path
- write meaningful failure reason: "Payment circuit open"

29. IMPLEMENTATION RULES FOR AGENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Always treat backend as source of truth.
2. Never generate placeholder demo state on frontend.
3. Prefer explicit DTOs over leaking EF entities.
4. Keep message contracts immutable.
5. Every saga transition must write:
   - state update
   - event log
   - outbox message where next step needed
6. Every consumer must implement idempotency check.
7. Every externally visible number on dashboard must come from:
   - DB
   - Redis
   - RabbitMQ
   - process/system metrics
   - in-memory monitor fed by real backend events
8. Do not build extra features outside this PRD unless needed to satisfy contracts.
9. Final product should run locally with one command sequence and deploy cleanly.
10. Keep architecture interview-defensible:
   - Saga over 2PC
   - Transactional Outbox
   - API key protection
   - integration tests with containers
   - explicit compensation
